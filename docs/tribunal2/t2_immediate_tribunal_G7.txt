INJECTED REQUIREMENT:
If any part of the system fails or provides invalid data, the system must respond in a safe and predictable way.
If a measurement becomes unavailable or invalid, the system shall not continue as though the value were correct. It shall have a defined response: continue with limited operation, stop the affected function, attempt recovery, or require intervention.

#1
Affected Requirement / Component: Whole system - definition of the safe state (FR16, NFR9)

What needs to change?:
Define one safe state that every failure response falls back to: both motors at zero commanded output and a controller state that cannot drive again by itself.

Suggested by:
Team

Decision:
No Change

Why?:
The design already has this. Every stop path ends in motion_apply(LINE_UNCERTAIN) or motion_stop_now(), and no state other than LINE_FOLLOWING, OBSTACLE, AT_JUNCTION and IDLE drives the wheels. The robot has no actuator that is hazardous when stopped, so zero output is always a valid fallback.

Engineering Evidence:
task_controller.c:27-38: nine controller states; STOPPED, NAV_SAFETY_STOP, ERROR, REMOTE_HOLD, LIFTED all call motion_apply(LINE_UNCERTAIN) every period (task_controller.c:813-838).
motor.c:60-81 motor_stop() writes compare 0 to GP8, GP9, GP10, GP11 (coast).
motor.c:47-50 motor_init() zeroes all four pins at boot; the live build boots in ROBOT_REMOTE_HOLD (task_controller.c:578).
Response class mapping: STOPPED / NAV_SAFETY_STOP = stop affected function (operator STOP then START); ERROR = require intervention (latched until reset, task_controller.c:494); LIFTED = attempt recovery.

#2
Affected Requirement / Component: Motor driver - brake vs coast on stop (NFR9)

What needs to change?:
Requirement NFR9 says "every stop path writes zero to all motor pins". AI suggested making every stop a coast (all pins 0) to match the wording.

Suggested by:
AI

Decision:
Modify

Why?:
Braking is the safer response at junction stops and downhill faults because it stops in a shorter distance. The operator STOP already skips the brake. Keep both, and change the requirement wording to say what the code does.

Engineering Evidence:
motor.c:83-97 motor_brake() writes MOTOR_PWM_WRAP + 1 to all four pins, holding both H-bridge inputs high (short brake).
APP_JUNCTION_BRAKE_MSEC = 200 ms (app_config.h:203), so the brake lasts 4 controller periods, then motor_stop().
motion.c:471-485 motion_stop_now() clears g_brake_cycles and calls motor_stop() first: operator STOP is an immediate coast.
New NFR9 wording: "Every stop path commands zero motor duty. A brake may hold both pins high for at most 200 ms before coasting. Operator and link-loss stops coast immediately."

#3
Affected Requirement / Component: RTOS - controller task hang (no hardware watchdog)

What needs to change?:
Enable the RP2040 hardware watchdog, fed only by the controller task at the end of each successful 50 ms cycle, timeout 250 ms.

Suggested by:
Buddy 2

Decision:
Accept

Why?:
A hung controller is the only failure that leaves the motors driving: the PWM slices keep outputting the last compare value. No software check can catch it because the checker is the thing that hung. A chip reset lands in the safe state.

Engineering Evidence:
The watchdog counter is never enabled. encoder.c:20 and :194-195 only write WATCHDOG TICK (0x4005802C) to clock the microsecond timer.
Timeout choice: 5 x APP_CONTROLLER_PERIOD_MSEC (50 ms, app_config.h:31) = 250 ms, so normal jitter (relative tk_dly_tsk, task_controller.c:626) cannot trip it. Blind travel before reset at 110 mm/s = about 28 mm.
Safe after reset: motor_init() zeroes pins (motor.c:47-50); RP2040 GPIO pads reset as inputs with pull-down enabled, so H-bridge inputs read low (coast) during reset; boot state is REMOTE_HOLD and needs a new START (require intervention).
Feeding from a separate high-priority task is rejected: a hung controller would still be fed.
Debug builds must pause the watchdog on debug, or breakpoints reset the board.

#7
Affected Requirement / Component: RTOS - controller loop timing and stack use (NFR3, NFR7)

What needs to change?:
Measure worst-case controller cycle time and task stack high-water marks on target, and publish them in the SENSOR frame.

Suggested by:
Buddy 2

Decision:
Modify

Why?:
Accept the measurement, but change the controller to an absolute-time period (or log the actual period) rather than redesign the loop now. The loop uses a relative delay, so overruns stretch the period rather than miss it; stack overflow would become a hard fault with motors at last duty (row #3 covers the consequence). We have no on-target evidence yet.

Engineering Evidence:
task_controller.c:623-627: for (;;) { controller_cycle(); tk_dly_tsk(APP_CONTROLLER_PERIOD_MSEC); } - real period = 50 ms + cycle time.
APP_TASK_STACK_BYTES = 4096 per task (app_config.h:7); buddy1_rt.c:30 B1_TASK_STACK 4096.
docs/min-bits/MINIMUM_BITS.md: "task stack high-water marks are not part of an ELF measurement" (no measurement exists).
Proposed method: fill stacks with a known pattern at boot, report deepest use per task once per second (1 x uint16 per task).

#11
Affected Requirement / Component: Motion - lost-line search gives up without reporting (FR4, FR16)

What needs to change?:
When the search gives up, the controller should enter ROBOT_STOPPED and report a fault, instead of the motion module silently holding the wheels at zero while the controller stays in LINE_FOLLOWING.

Suggested by:
Buddy 1

Decision:
Accept

Why?:
Today the robot stops safely but the operator cannot tell why, and the controller still believes it is following. That is not predictable from the operator's side.

Engineering Evidence:
motion.c:848-866: SEARCH_GAVE_UP -> stop_wheels(); drive_wheels(LINE_UNCERTAIN); return true. No report_fault() and no state change in task_controller.c.
Fix: motion exposes a gave-up flag; controller returns ROBOT_STOPPED with report_fault(15) ("line not found"), the last free 4-bit code (row #8). Recovery: STOP, place on line, START (same as fault 2).
Cost: no new state. line_search_t.phase:3 already holds SEARCH_GAVE_UP (motion.c:164, 170-181); the controller only needs a read accessor.

#12

Suggested by:
Buddy 2

Decision:
No Change

#13
Affected Requirement / Component: Encoders - dead encoder disables the lost-line search (FR4, FR7)

What needs to change?:
Add an encoder plausibility fault and a time-based backup for the lost-line search.

Suggested by:
Buddy 2

Decision:
Accept

Why?:
The lost-line search measures distance with the encoders. If the encoders are dead, its distance never grows, so the search never starts and the robot drives straight off the course. One sensor's failure silently disables another sensor's safety check. A second, independent source (the kernel clock) removes that dependency.

Engineering Evidence:
motion.c:809-826: g_search.white_counts += moved, where moved = search_travel() from encoder counts (motion.c:877-890). With moved = 0 the 50 mm / 100 mm thresholds are never reached.
Proposed plausibility rule: stall boost at its 15 % cap (15 periods, 750 ms) AND that wheel's count unchanged AND the other wheel turning -> latched fault, ROBOT_ERROR. The existing "Wheel stalled" print at motion.c:1061-1071 marks this exact moment. Requiring the other wheel to turn avoids false trips on a tight curve, where the inner wheel is legitimately stopped (MOTION_STOP_RPM = 6 RPM, motion.c:61).
Proposed time backup: both IR white for > 1500 ms while driving -> stop. 1.5 s x 110 mm/s = 165 mm, beyond the 100 mm search point, so it never fires before the normal search. Cost: one uint32 timestamp.
ERROR not STOPPED: a broken wire does not heal, and junction confirmation, 134 mm centring, pivot angle and odometry all depend on encoder counts.

#21
Affected Requirement / Component: I2C bus / IMU driver timeout

What needs to change?:
Reduce the I2C transaction timeout and add bus recovery (9 SCL clocks, then re-initialise the LSM303) after repeated failures.

Suggested by:
Buddy 2

Decision:
Modify

Why?:
Accept the shorter timeout. Bus recovery is accepted as a later step only: it needs pin-level control of I2C0 outside the kernel device driver, and the existing 1 s controller rule already stops the robot if recovery fails. A 1000 ms timeout on a 20 ms task means one stuck transfer blocks the IMU task for a full second before anything is reported.

#25
Affected Requirement / Component: Ultrasonic sensor - missing echoes (FR9, NFR5)

What needs to change?:
AI suggested treating a missing echo as "no obstacle" (maximum range) so the robot keeps driving.

Suggested by:
AI

Decision:
Reject

Why?:
A missing echo means we know nothing, not that the path is clear. An unplugged sensor would otherwise look like an empty course forever. The design separates "out of range" (a pulse started, nothing came back in range: treated as clear) from "no echo" (no pulse at all: fault after 5 in a row).

Engineering Evidence:
ultrasonic.c:70-129: ECHO stuck high for OBS_ECHO_CLEAR_MSEC 50 ms -> NO_ECHO; no ticks in OBS_ECHO_TIMEOUT_MSEC 30 ms -> NO_ECHO ("wiring, power or sensor fault", line 124); ticks but no end / > 4000 mm -> OUT_OF_RANGE.
obs_config.h:30-34: OBS_STOP_MM 250, OBS_NO_ECHO_LIMIT 5, OBS_FAILSAFE_NO_ECHO 1 ("Persistent missing echoes are unverified rather than free space").

#34
Affected Requirement / Component: Reserved bits and sentinel values (NFR13, Change Requirement 1)

What needs to change?:
Check reserved bits in the header flags byte, as is already done for payloads.

Suggested by:
Team

Decision:
Accept

Why?:
Payload reserved bits are checked, but the header flags byte uses only bit 0 and its 7 reserved bits are not checked on either side. A frame with unknown flags should be rejected rather than silently misread.

Engineering Evidence:
Snapshot: 99 bits in 13 bytes (104 bits); top 5 bits must be zero, mask 0xF8 (buddy1_protocol.c:130-133, protocol.js:27).
Mapping: four 5-bit letters = 20 bits in 3 bytes; top 4 bits must be zero, mask 0xF0; letters > 25 or duplicates rejected (buddy1_protocol.c:57-79).
Sentinels: 1023 in 10-bit fields = unavailable, 31 in the 5-bit letter = none; dashboard converts to null (protocol.js:31-33).
Header flags: out->flags = s->uncertain ? 1 : 0 (buddy1.c:141); decode copies bytes[3] with no check (buddy1_protocol.c:50, protocol.js:22). Fix: reject if (flags & 0xFE) != 0, one line each side.
